# Архитектура

Кратко; полное обоснование в [plan.md](plan.md).

- **Сервер** (`server/`): HTTP API на chi. Слои: `httpapi` (обработчики) → `store` (код, сгенерированный sqlc) → Postgres. Настройки только из переменных окружения (`internal/config`).
- **Миграции**: goose, встроены в бинарник (`server/migrations`), применяются при старте.
- **Справочник**: общий для всех, поиск с опечатками через `pg_trgm` (`word_similarity`).
- **Позиции списка**: `id` создаёт клиент (чтобы работать офлайн), `version` растёт при каждом изменении (`item_version_seq`), удаление мягкое. На этом строится синхронизация (раздел 2 плана).
- **Вход**: email + одноразовый код, только собственные аккаунты (`internal/auth`). Код из 6 цифр живёт 10 минут, хранится в виде HMAC, после 5 неверных попыток блокируется, новый можно запросить раз в минуту. На выходе access JWT (15 минут) и одноразовый refresh-токен (90 дней, хранится хешем); повторное использование старого refresh-токена отзывает все токены пользователя. Таблица `auth_identities` допускает добавление Google/Apple позже.
- **Письма**: в разработке код пишется в лог (`LogMailer`), в production (`APP_ENV=production`) обязателен SMTP.
- **Удаление аккаунта** (`DELETE /api/v1/me`): общие списки переходят другому участнику, остальное удаляется.

Что ещё не сделано: списки и участники, `/sync`, WebSocket, push, мобильное приложение.
