# Архитектура

Кратко; полное обоснование в [plan.md](plan.md).

- **Сервер** (`server/`): HTTP API на chi. Слои: `httpapi` (обработчики) → `store` (код, сгенерированный sqlc) → Postgres. Настройки только из переменных окружения (`internal/config`).
- **Миграции**: goose, встроены в бинарник (`server/migrations`), применяются при старте.
- **Справочник**: общий для всех, поиск с опечатками через `pg_trgm` (`word_similarity`).
- **Позиции списка** (`internal/items`): `id` создаёт клиент (чтобы работать офлайн), удаление мягкое. `version` берётся из счётчика самого списка (`lists.item_seq`): запись в список блокирует его строку до коммита, поэтому версии внутри списка фиксируются строго по порядку и запрос «всё новее версии N» не пропускает поздно закоммиченные изменения. Глобальная последовательность для этого не годилась бы (транзакции с меньшим номером могут завершиться позже). `GET .../items?since=N` отдаёт изменения, включая удалённые, и `cursor` для следующего запроса. На этом строится синхронизация (раздел 2 плана).
- **Редактирование позиций**: `PUT` создаёт или заменяет позицию целиком и идемпотентен (повтор из офлайн-очереди безопасен), `PATCH` меняет только присланные поля, `null` очищает значение. Чужой или удалённый id через `PUT` не перехватить (409). «Очистить купленное» переносит купленное в `purchase_history` и мягко удаляет позиции одной версией. Количество и цена хранятся как `numeric`, в JSON приходят числами.
- **Вход**: email + одноразовый код, только собственные аккаунты (`internal/auth`). Код из 6 цифр живёт 10 минут, хранится в виде HMAC, после 5 неверных попыток блокируется, новый можно запросить раз в минуту. На выходе access JWT (15 минут) и одноразовый refresh-токен (90 дней, хранится хешем); повторное использование старого refresh-токена отзывает все токены пользователя. Таблица `auth_identities` допускает добавление Google/Apple позже.
- **Письма**: в разработке код пишется в лог (`LogMailer`), в production (`APP_ENV=production`) обязателен SMTP.
- **Списки и участники** (`internal/lists`): роли `owner` и `editor`. Не участник получает 404 (а не 403), чтобы нельзя было проверять существование чужих списков. Переименовать и удалить список (мягко, `deleted_at`) может только владелец; выйти может любой участник, кроме владельца. Участники друг другу видны по имени, а без имени по замаскированному email.
- **Приглашения**: код из 8 символов без похожих (0/O, 1/I), по умолчанию 7 дней и 10 использований, не более 50 участников в списке. Создать приглашение может любой участник (чтобы семья могла звать своих без владельца), счётчик использований защищён блокировкой строки и не обходится параллельными запросами.
- **Удаление аккаунта** (`DELETE /api/v1/me`): общие списки переходят другому участнику, остальное удаляется.

Что ещё не сделано: WebSocket, push, мобильное приложение.
